# Зачёт, балл и обратная связь

Ответ на вопрос «как реализовать пороги при ветвлении и как собрать
детальный разбор». Всё считается чистой функцией `buildReport` из
сценария и попытки, поэтому отчёт воспроизводим из истории.

## Результат попытки

Определяется в момент завершения, по первому сработавшему правилу:

| Порядок | Правило | Результат |
|---------|---------|-----------|
| 1 | Истёк таймер сценария или ситуации | `failed`, причина `timeout` |
| 2 | Шкала достигла `min` | `failed`, причина `meterDepleted` с именем шкалы |
| 3 | Финальный узел с `result` | как указано, причина `endNode` |
| 4 | `passCriteria` есть и не выполнены | `failed`, причина `criteria` со списком невыполненного |
| 5 | Иначе | `passed` |

Пороги проверяются по итоговым значениям, а не по пути: любая ветка,
которая привела к финалу с нужными шкалами и флагами, засчитывается.
Это и делает ветвление совместимым с фиксированными минимумами. Если
автору важен конкретный шаг, он выражает это флагом в `passCriteria`
или финальным узлом с `result: "failed"`.

## Балл

Балл нужен, чтобы сравнивать попытки и показывать качество решений даже в
сценарии без шкал.

- Учитываются только решения с `review`. Вес: `best` 1, `ok` 0.5, `bad` 0.
- Балл = сумма весов / число учтённых решений × 100, округлённый.
- Нет ни одного решения с `review` → балл не показывается, сравнение
  попыток идёт по статусу и времени.

Один и тот же узел, пройденный дважды (возврат к вопросу наставника),
даёт два решения: повторная ошибка тоже ошибка.

## Лучшая попытка

Сравнение по порядку: `passed` выше `failed`; выше балл; меньше
длительность. Хранятся все попытки, «лучшая» — вычисляемое поле, а не
отдельная запись.

## Содержимое отчёта

| Блок | Источник |
|------|----------|
| Итог и причина | `ending`, таблица выше |
| Шкалы | итоговые `meters` против `passCriteria.meters`; ряд значений из `log` для графика |
| Разбор решений | каждая запись `log` с `review`: текст вопроса, выбранный вариант, оценка, пояснение, эффекты |
| «Лучше было бы» | для `ok` и `bad`: текст и пояснение варианта с `verdict: "best"` в том же узле, если он есть |
| Темы | по каждому `topic` из решений: число `best`, `ok`, `bad` |
| Рекомендации | см. ниже |

Отчёт описывает только пройденный путь. Непосещённые ветки не
оцениваются и не показываются: сотрудник узнаёт о них через «лучше было
бы» и повторное прохождение.

## Рекомендации

1. **Слабые темы** — темы, где есть хотя бы одно `bad`, либо доля `best`
   ниже половины.
2. **Кандидаты** — сценарии каталога, чьи `topics` пересекаются со
   слабыми, кроме текущего. Сортировка: больше пересечение, затем ещё не
   зачтённые, затем короче по `estimatedMinutes`. Не больше трёх.
3. **«Пройти ещё раз»** предлагается всегда; при `failed` или балле ниже
   ста это первая кнопка.
4. **«Следующий сценарий»** появляется, если попытка `passed` и открыта
   из курса: берётся следующий по порядку.

Каталог для рекомендаций в MVP0 — все сценарии в `src/content/`, не
только текущий курс.

## Что хранит попытка

`Attempt`: `id`, `scenarioId`, `scenarioVersion`, `courseId?`,
`startedAt`, `finishedAt`, `status`, `reason`, `score?`, `meters`,
`flags`, `log`. Этого достаточно, чтобы собрать отчёт без UI-состояния.
При расхождении `scenarioVersion` с текущим сценарием отчёт показывает
только итог и шкалы, без текстов решений.

## Открытые вопросы к спецификации

- Считать ли решения наставника в балл наравне с ситуацией или показывать
  отдельно блоком «Теория». Предварительно: наравне, разделение по темам.
- Показывать ли «лучше было бы» при `ok`. Предварительно: да.
